Add authoritative steering/follow-up mode transitions before exposing them through `/settings` or another client.

State owner and transitions:

- `AgentSession` owns the live queue modes because `pi-agent-core.Agent.steeringMode` and `followUpMode` determine delivery behavior. `SettingsManager` owns persisted layered configuration.
- Add readonly `session.steeringMode` and `session.followUpMode` accessors derived from the live agent; do not mirror them in a second mutable field.
- Add explicit mutations for steering and follow-up modes. Keep the valid domain closed to `"all" | "one-at-a-time"`.
- Define scope explicitly for Zi's global/project layering rather than guessing an active scope. A concrete `SettingsScope` parameter is acceptable; avoid an option-bag framework. Preserve Pi's global behavior as the default only if project overrides remain coherent and visible.
- Transition order must be atomic from observable Zi state: admit against the current session state, persist the chosen scope successfully, derive the new effective layered value, update the live agent, then publish a typed credential-free event if clients need notification.
- If settings persistence fails or the scope is invalid, live agent behavior must remain unchanged. If a global write is shadowed by a project override, live state must equal `SettingsManager.get()` and the result must expose that the requested value is not effective; never leave file, manager, and agent disagreeing.
- Decide and test admission while a provider run is active. Pi permits synchronous live changes; prefer that behavior if pi-agent-core safely reads the mode at queue-drain boundaries. Disposal must reject.
- No-op effective transitions must not append session entries or emit misleading events. Queue modes are settings, not transcript history.
- Existing queue identities, bounds, delivery acknowledgement, interruption, and failed-run recovery must remain unchanged.

Acceptance tests:

- Global and project mutations persist unknown-field-preserving settings and immediately update the corresponding live agent mode.
- A project override remains authoritative after a global write; returned/effective state and live behavior match layered settings.
- Invalid/oversized settings refusal leaves both live modes unchanged.
- Changing steering mode during a run changes the next eligible steering drain exactly as Pi does; same for follow-up mode.
- Recreating a runtime from disk restores the effective modes.
- Concurrent queue delivery plus a synchronous mode mutation has one deterministic boundary and does not duplicate/drop entries.
- Disposed sessions reject; subscriber failure after a committed transition does not roll back durable/live state.

## Implemented

- Added public live-derived `steeringMode`/`followUpMode` getters and required-scope mutations on `AgentSession`.
- Mutations validate JavaScript input, persist global/project settings first, derive the effective layered value, update Pi's live agent, and return `{ scope, requested, effective }`.
- Added effective-only session events; observer failures cannot roll back a committed transition.
- Preserved active-run admission so changes apply at the next pi-agent-core drain boundary.
- Added global/project, shadowing, invalid input, persistence failure, restoration, no-journal, disposal, observer failure, and active-run delivery coverage.
- Updated TUI event exhaustiveness and architecture/parity documentation.

Verification: `bun run check` passes (76 coding-agent tests, 88 TUI tests, 2 CLI tests).
