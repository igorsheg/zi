## The next task: `zi-k9f.5`

### Goal
Define the session-targeting contract clearly enough that a user can explain it without reading code, and encode that contract in planner types + diagnostics.

### Why this is the right next pressure
`zi-k9f.8` is improved but still blocked by `zi-k9f.5`: help and diagnostics cannot be fully truthful until session-target semantics are final.

## Important current implementation details

### Current raw surface
`src/cli/parse.zig` still models session targeting as:
- `RawRunArgs.continue_path: ?[]const u8`

### Current planned surface
`src/cli/plan.zig` currently models session targeting as:
- `SessionTarget.none`
- `SessionTarget.continue_path`

### Current planner behavior
The planner already does some useful rejection:
- rejects prompt + session target
- rejects `--continue` + `--no-session`
- rejects `-p/--print` + `--mode`
- requires a prompt for batch

That means the *effective* behavior today is already pushing `--continue` toward interactive-only semantics.

### Important drift still present
`src/cli/run_batch.zig` still has continue/session restore machinery even though the planner now makes that path effectively unreachable for valid plans.

That is a clue, not a feature:
- do **not** preserve that path for compatibility theater
- once session-target semantics are final, delete or reshape dead paths rather than keeping fallback behavior around

## Recommended immediate move

### 1. Decide the product contract first
Before editing code, decide whether session targeting in zi should mean only:
- explicit session path resume via `--continue <path>`

or whether it should become a broader explicit surface such as:
- resume most recent/current session
- resume a specific path
- resume a specific session id

If the surface grows, encode it in types, not booleans.

### 2. Make the planner own the whole matrix
Push all semantics into `src/cli/plan.zig`.

The planner should answer things like:
- is a prompt allowed with this target?
- is this target interactive-only?
- are there conflicting selectors?
- does this combination have defined semantics?

Do **not** let executors rediscover policy.

### 3. Tighten diagnostics around the chosen contract
Once the semantics are fixed, update:
- `src/cli/diagnostics.zig`
- `src/cli/help.zig`

so they describe the exact contract, not approximations.
