# Tool presentation is semantic data

Status: Accepted

OpenZi's first stable tool rows projected raw arguments and results into a closed union named after built-in tools, then switched on those tool variants again inside `ToolCallView`. That boundary kept OpenTUI out of `coding-agent`, but every polished tool still required coordinated parsing and rendering changes in both packages. Pi Mono shows the value of tool-local typed semantics and stable per-call rendering, Grok Build shows stable keyed refinement and semantic render blocks, and OpenCode v2 shows why model-facing content must remain separate from validated structured output. Their native-component callbacks, broad block frameworks, tool-specific frontend dispatch, compatibility parsers, and per-tool timers do not fit OpenZi.

Built-in tools now have two deliberate contracts. Each tool produces bounded, typed result `details` independently from model-facing `content`; expected operational failures remain typed outcomes and one coding-agent finalization seam maps them to Pi's `isError`. A pure coding-agent projector validates partial arguments and persisted results, then returns one shallow `ToolPresentation` containing a semantic header, at most one `terminal | source | diff | text` body, structured notices, explicit compact/detailed windows, and generic timing semantics. Presentation is derived and is never authoritative or persisted separately.

The TUI knows lifecycle status and generic presentation primitives, not built-in tool names, argument schemas, result-detail types, or model-facing footer syntax. It owns theme, cell geometry, syntax highlighting, wrapping, selection, density, native identity, and renderable disposal. Grok Build's dense verb-first rows inform the generic chrome: compact successes are one line, running and failed bodies may expose bounded peeks, and detailed mode reveals independently bounded content. The accepted transcript-item amendment keeps that shallow semantic boundary while rendering subordinate evidence on the inherited terminal surface with a lifecycle-colored open rail, semantic separator, and short closing cap rather than a panel or framed box. Bash is the first slice to use an optional human title with an exact secondary command. Read is the second: whole-file success collapses to one path row, while detail exposes bounded first/last source with absolute line numbers and continuation facts. Write is the third: bounded streamed arguments update a `lines so far` fact, success collapses to authoritative path and size facts, detail exposes bounded numbered argument content, and failures expose only the operational error. Edit is the fourth: streamed arguments remain a header-only replacement count through preparation and execution, only a validated successful result introduces the authoritative context-rich diff, compact success keeps a bounded diff review beneath its diffstat, and detailed generic diff chrome owns line gutters and wrapping without reading the file. Like Pi's per-tool renderer selection, a known built-in never changes into an unknown-tool JSON row: its projector is total, ignores malformed details as a whole, and degrades inside the same semantic chrome. A new built-in normally adds one typed result union and one coding-agent projector; the TUI changes only for a deliberately new visual primitive. Only unknown tool names use the bounded generic projection. This refactor has one atomic cutover and no legacy display adapters, compatibility shims, renderer registry, recursive UI schema, or dual rendering path.
