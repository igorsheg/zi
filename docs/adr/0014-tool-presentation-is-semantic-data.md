# Tool presentation is semantic data

Status: Accepted

OpenZi's first stable tool rows projected raw arguments and results into a closed union named after built-in tools, then switched on those tool variants again inside `ToolCallView`. That boundary kept OpenTUI out of `coding-agent`, but every polished tool still required coordinated parsing and rendering changes in both packages. Pi Mono shows the value of tool-local typed semantics and stable per-call rendering, Grok Build shows stable keyed refinement and semantic render blocks, and OpenCode v2 shows why model-facing content must remain separate from validated structured output. Their native-component callbacks, broad block frameworks, tool-specific frontend dispatch, compatibility parsers, and per-tool timers do not fit OpenZi.

Built-in tools now have two deliberate contracts. Each tool produces bounded, typed result `details` independently from model-facing `content`; expected operational failures remain typed outcomes and one coding-agent finalization seam maps them to Pi's `isError`. A pure coding-agent projector validates partial arguments and persisted results, then returns one shallow `ToolPresentation` containing a semantic header, at most one `terminal | source | diff | text` body, structured notices, and a compact preview policy. Presentation is derived and is never authoritative or persisted separately.

The TUI knows lifecycle status and generic presentation primitives, not built-in tool names, argument schemas, result-detail types, or model-facing footer syntax. It owns theme, cell geometry, syntax highlighting, wrapping, selection, expansion, native identity, and renderable disposal. A new built-in normally adds one typed result union and one coding-agent projector; the TUI changes only for a deliberately new visual primitive. Unknown tools use the ordinary bounded generic projection. This refactor has one atomic cutover and no legacy display adapters, compatibility shims, renderer registry, recursive UI schema, or dual rendering path.
